  Summary:
  - s2 is written in pure functional style on top of what s1 already has, and it
    uses all four telescopes.
  - There are two substrates:
    - Datalog does all checking: types, destructuring, exhaustiveness, protocol

      reduces and expands.

    - () is runtime values.
    - [] is types and comptime: pure, with macro expansion, hashing and
      verification.

    (line: String) <f: Closed>.

    - {} moves resources and runs handlers.

  Questions

  Q1. Which engine unifies types? D cannot build terms.

  Proposal: one pass gives an id to every type node of a def, plus one fresh
  node per [] binder at each call. D unifies only those nodes, with union-find
  (egglog, Zhang et al. PLDI 2023; congruence closure, Nelson–Oppen 1980). D
  never makes a node, so it always terminates. Kanren makes the new terms (given
  heads, macro output, synthesis), and its answers enter D as facts.

  def id [A: Type] (x: A): A = x
  val b: Bool = id(41)   // fresh A=3; eq(3, I64) from the arg, eq(3, Bool) from
  val's type: one class, two heads: clash

  I recommend yes. For speed, D should get a native union-find; storing the
  equality closure as rows grows quadratically per class.

  Q2. Where does the expansion go? s1 returns it as a tree (e2); D can only
  return facts.

  Proposal: the expansion becomes facts keyed by node id, such as instAt(call, 
  fn, ty), capArg(call, i, cap) and allocIn(ctor, r). The emitter reads only
  these facts, and a use with no fact is a clash. For macros, Kanren picks a
  clause and D checks its output on an extended model; a clash kills that branch
  (as ruled in Q-MA7). D models are persistent maps, so a branch can extend a
  shared model cheaply. That needs a new D.extend(model, facts) that continues
  the semi-naive solve. I recommend yes.

  Q3. Region sets. The vision writes x@{r1 & r2} and |; the ruled syntax is
  List[I64]^<r>. For liveness, & and | demand the same thing: every region named
  must be alive (s1 already joins var caps by union, check.srs:171). "Overlap"
  means one region nests in another, which is an outlives fact.

  def pair {a: Region} {b: Region} (x: Box^<a>, y: Box^<b>): Pair^<a, b> =
  Pair(x, y)
  def widen {a: Region} {b: Region} <outlives(a, b)> (x: Box^<a>): Box^<b> = x

  I recommend keeping ^<...> as one capture set (Odersky et al. 2022), dropping
  & and |, and writing nesting as <outlives(a, b)> (Cyclone, Grossman et al.
  PLDI 2002; Rust's 'a: 'b).

  Q4. How deep do handlers go? Today an op returns straight to its caller (the
  README Door example). Resuming anywhere needs captured continuations, which
  conflicts with no GC and portable C. Three options:

  - A. Handlers resume once, at the tail, or abort. They compile to direct calls
    (Xie et al. ICFP 2020; Effekt).
  - B. One-shot continuations by stack switching (libmprompt, Leijen). This is
    not portable C.
  - C. Multi-shot continuations. These need stack copies or a GC.

  handler Stdout for Log:
    def init(): Ptr = rt_arena_new()
    def log(self: Ptr, x: I64): Unit = rt_print_i64(x)   // resumes once, at the
  tail

  I recommend A now and B as a bead. Under A, an abort must end every capability
  opened since its handle, as a flow rule.

  Q5. Can user <> rules break soundness? Yes, if a user rule can derive a
  checker relation. A user rule that derives moved hides every stuck clash
  (s2/flow.srs:265).

  Proposal: checker relations (at, flow, step, moved, endOk, …) are read-only
  for users. User rules derive only user relations, and an invariant is a user
  relation that the checker reports as a clash.

  <rule def bothOpen(f, g) = at(f, Open), at(g, Open)>
  <never bothOpen(f, g)>   // idea only, not ruled: the syntax is yours

  I recommend making checker relations read-only. Which syntax should mark a
  user relation as an invariant?

  Q6. What does a () block hide? Proposal: it hides the parent's {} and <>. A
  parent val is visible only if every region in its capture set is named by the
  block (the capture-checking rule).

  handle a = Arena()
  val xs = build(3)      // List^<a>
  (xs) {a} =>            // syntax not decided
    sum(xs)              // ok: the block names a

  I recommend these semantics. What syntax should a () block use to name what it
  takes?

  Q7. Comptime.
  - (a) Vision line 49 says macros live in {}, but it sits in the [] section.
    Q-MA4 ruled that a macro call is a Kanren goal, which is type level. I
    recommend [].
  - (b) If comptime code reads a file, the output depends on the disk, and the
    content hash stops being true. Proposal: compiler capabilities are {}
    binders, and the bytes of every read are hashed into the def's hash (as
    Unison does; Zig @embedFile). I recommend yes.

  Q8. Phase order. The vision says type level is the last phase before emission.
  But Bits(dbl(4)) needs dbl checked and pure first, and a macro needs the
  checker inside its search. s1 expands types before checking (types.srs:2-3).

  Proposal: no fixed phases. Decls form a dependency graph, and each strongly
  connected group is solved to its fixpoint, in order. A cycle through comptime
  eval is a reject.

  def size(x: Bits(size(0))): I64 = 8   // size needs Bits(size(0)), which needs
  size: reject

  I recommend yes.

  Q9. The example signature. In def writeAndClose [F: File] {fs: FileSystem[F]} 
  <f: Open> (line: String) <f: Closed>:
  - f is bound by no group, but a telescope may use only names bound before.
  - [F: File] asks for a kind called File, and today [] binders take only Type
    (types.srs:149).
  - <f: Open> is new syntax.

  In today's ruled syntax it would be:

  def writeAndClose {fs: FileSystem} {f: File} <at(f, Open)> (line: Str): Unit
  <at(f, Closed)>

  - Q9b. What does [F: File] mean? I recommend dropping it here, because {f: 
    File} already says what f is.

● Here are five examples of the four blocks combined, each aimed at a real C
  pain point. None of this syntax is ruled. Lines marked "idea" are mine.

  The four blocks, as I read the vision:
  - [ e ]: runs in the compiler. It is pure and ends in a value or a compile
    error.
  - { … }: a resource scope. handle lines live here, and every capability ends
    at the closing }.
  - (names) => e: an isolated scope. It sees only the names it lists, plus what
    those names' types need.
  - < … >: Datalog rules and invariants over the checker's facts. User rules may
    read checker relations but not derive them (Q5).

  ---

  E1. Per-request memory with no leaks and no lifetime noise

  C pain: malloc and free per request leak, and free on an error path gets
  forgotten.
  - Zig: ArenaAllocator plus defer deinit(), by hand, and nothing stops a
    pointer from escaping.
  - Rust: 'a spreads into every type, or you clone.

  def serve {heap: Region} {c: Conn} <at(c, Open)> (): Summary^<heap> <at(c,
  Closed)> =
    val routes = [ perfectHash(List("/", "/api", "/health")) ]   // [] table 
  built at compile time, no startup cost
    val s = {
      handle tmp = Arena()                    // {} per-request arena
      val raw = c.read{tmp}()
      val req = (raw, tmp) =>                 // () parser sees raw and tmp only:
        parse(raw)                            //   no heap, no Conn, no IO, no globals
      keep{heap}(summarize(req, routes))      // the only value that crosses into heap
    }                                         // tmp ends here, with one free
    c.close()
    s

  The compiler rejects:
  - returning req: its type names tmp, which has ended (escape);
  - a parse that logs or allocates in the heap: heap is not in the () scope;
  - a forgotten c.close(): c ends in Open, which is not an end state.

  You write no lifetime annotations. Regions are capabilities, found the way
  Scala 3 finds givens.

  E2. Locks: no data access without the lock, and no deadlock

  C pain: a field read without its lock; two threads taking A then B and B then
  A.
  - Rust: MutexGuard covers the first. Nothing covers lock order.
  - Zig: neither.

  protocol Mutex:
    state Free, Held
    start Free
    end Free
    op lock(): Unit : Free -> Held
    op unlock(): Unit : Held -> Free

  // readable only while m is held
  type Guarded [A: Type] {m: Mutex} <at(m, Held)> = A

  <
    // "lock b while a is held", read from the checker's at/step facts, across 
  every fn
    rule def order(a, b) = at(p, a, Held), step(p, _, b, lock)
    rule def reach(a, b) = order(a, b)
    rule def reach(a, c) = order(a, b), reach(b, c)
    never reach(a, a)                       // idea: a cycle in lock order is a compile error
  >

  The deadlock check is a whole-program Datalog query over facts the checker
  already has. RacerX (Engler and Ashcraft, SOSP 2003) did this as an external
  tool; here it is a library rule.

  E3. Embedded: init order, compile-time hardware math, a clean interrupt 
  handler

  C pain: sending on an unconfigured UART, a baud divisor computed wrong, printf
  or malloc inside an IRQ.
  - Rust embedded-hal: one type per state (Uart<Disabled>), a lot of generic
    noise, and nothing per-scope that forbids allocation.
  - Zig: has comptime, but no init-order check.

  protocol Uart:
    state Off, Ready
    start Off
    end Off
    op init(div: I64): Unit : Off -> Ready
    op send(b: I64): Unit : Ready -> Ready
    op stop(): Unit : Ready -> Off

  def boot {u: Uart} <at(u, Off)> (): Unit <at(u, Ready)> =
    val div = [
      val d = 48000000 / (16 * 115200)
      require(errPct(48000000, 115200, d) < 2)   // idea: a compile error 
  instead of a garbled wire
      d
    ]
    u.init(div)

  def onRx {u: Uart} <at(u, Ready)> (b: I64): Unit =
    (u, b) =>          // () sees no Region, Heap or Log: an IRQ that cannot 
  allocate or print
      u.send(b)

  States are facts, not types, so a function stays one function: <at(u, s), 
  next(s, send, s2)> serves every state that has a send. This already works in
  the README's readAny.

  E4. Error cleanup: goto fail, half-done transactions

  C pain: Apple's goto fail (2014), and a forgotten rollback.
  - Zig: errdefer, by hand.
  - Rust: Drop cannot fail and cannot force an explicit commit. #[must_use] is
    only a warning, because Rust types are affine, not linear.

  protocol Tx:
    state Open, Done
    start Open
    end Done
    op commit(): Unit : Open -> Done
    op rollback(): Unit : Open -> Done
    drop rollback            // scope end or abort while Open: the compiler 
  inserts the rollback

  def transfer {db: Db} {fail: Fail} (a: Acct, b: Acct, n: I64): Unit =
    {
      handle tx = db.begin()
      tx.debit(a, n)         // may raise fail: the abort path ends tx through 
  its drop op
      tx.credit(b, n)
      tx.commit()
    }

  Remove the drop line and Tx becomes linear: every path must call commit or
  rollback explicitly, and a missing one is a compile error. No mainstream
  language gives this choice per resource.

  E5. Parsing bytes with proved bounds (all four blocks)

  C pain: buffer overreads, the top CVE class.
  - Rust: a bounds check at run time, or unsafe get_unchecked.
  - Zig: checked in debug builds, undefined behaviour in ReleaseFast.

  enum Header:
    case Header(magic: I64, len: I64, flags: I64)

  val codec = [ derive.binary[Header](BigEndian) ]   // [] encoder + decoder (~)
  made at compile time

  // <> after () because it names buf: the telescope order decides what a fact 
  can see
  def readHeader {r: Region} (buf: Bytes^<r>) <len(buf, n), n >= 12> (): Header
  =
    codec.decode(buf)        // reads 0..11: proved inside n, so no run-time 
  check is emitted

  def onPacket {c: Conn} <at(c, Open)> (): I64 =
    {
      handle tmp = Arena()
      val buf = c.read{tmp}()
      if len(buf) >= 12 then (buf, tmp) => flagsOf(readHeader(buf)) else -1   //
  the if adds n >= 12 on its branch
    }

  This is refinement typing (Liquid Types, Rondon et al. PLDI 2008). The n >= 12
  part is integer arithmetic, so it is solved by Kanren's finite domains
  (s2/kfd.srs), not by flat Datalog.

  What each block gives

  block: []
  C pain point: macro hell, startup tables, wrong constants
  Rust / Zig today: proc-macros (a separate language) / comptime (no proofs)
  srs: the same srs, pure, always ends, content-hashed, derives both directions
  ────────────────────────────────────────
  block: {}
  C pain point: leaks, goto fail, hidden allocators
  Rust / Zig today: lifetimes and Drop / allocator params and defer
  srs: regions and handlers found like givens; cleanup at the scope end by

  ────────────────────────────────────────
  block: ()
  C pain point: IRQ and signal safety, sandboxing a parser
  Rust / Zig today: crate-wide no_std only / none
  srs: per-scope capability isolation (object capabilities)
  ────────────────────────────────────────
  block: <>
  C pain point: lock order, init order, bounds, invariants nobody can check
  Rust / Zig today: typestate by types / none
  srs: user Datalog over the compiler's own facts, every violation reported with

  its proof

  The edge is that all four sit on one solver, so a rule in <> can see facts
  from flow, regions, types and comptime at once. Rust's checks are fixed inside
  the compiler, and Zig's comptime cannot prove anything.
